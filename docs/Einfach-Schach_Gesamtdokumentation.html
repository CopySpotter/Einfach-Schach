2. Ziel und Charakter des Projekts

„Einfach Schach“ wurde als Schachanwendung mit besonderem Fokus auf eine leicht verständliche Bedienung entwickelt. Der ursprüngliche Projekttext nennt ausdrücklich eine gute UX für ältere Menschen. Der Code enthält darüber hinaus konkrete Funktionen für sehbeeinträchtigte und blinde Nutzer:innen: akustische Signale, Figuransagen, verborgene Screenreader-Texte, Fokusführung und einen eigenen Blindenmodus.

Die Anwendung verbindet drei Bereiche: Schach spielen, Schach trainieren und individuelle Bedienhilfen. Benutzerfortschritt und laufende Partien werden lokal gespeichert; Gesichtserkennung existiert als optionaler separater Dienst.

5. Benutzerabläufe

A. Gast spielt eine Partie

  1. Startseite öffnen und „Als Gast spielen“ wählen.
  2. Temporärer Gastbenutzer wird im Zustand-Store gesetzt.
  3. „PARTIE SPIELEN“ öffnet Chessground mit aktuellem FEN.
  4. Spieler:in zieht Weiß; chess.js prüft die Legalität.
  5. Nach dem Spielerzug berechnet die lokale KI ihren Zug.
  6. Anzeige, Sounds und Blindmode-Texte werden aktualisiert.
  7. Bei Spielende erscheinen Dialoge; beim Gast erfolgt keine Dateispeicherung.

B. Registrierung

  1. „Neues Konto“ wählen.
  2. Anzeigename eingeben und auf Eindeutigkeit prüfen.
  3. Spielstärke auswählen.
  4. Frage zur Sehbeeinträchtigung beantworten.
  5. Bei „Ja“ werden Blindenmodus und beide Soundgruppen aktiviert.
  6. Datenschutz-Schritt durchlaufen.
  7. /api/users/register erzeugt ID und speichert Benutzer in users.json.
  8. Falls ein Gesichtsscreenshot vorhanden ist, wird zusätzlich der Face-Service angesprochen.

C. Training

  1. „ÜBUNGEN“ wählen.
  2. Kapitelübersicht aus /api/training/all laden.
  3. Kapitel wählen und Übung starten/fortsetzen.
  4. Benutzerzug wird gegen erlaubte Lösungsvarianten geprüft.
  5. Falscher Zug → Hinweis und neuer Versuch.
  6. Korrekter Zug → gespeicherter Gegenzug wird automatisch gespielt.
  7. Nach Abschluss wird Kapitel-/Gesamtfortschritt aktualisiert.
  8. Abgeschlossene Kapitel können mit Zufallsaufgaben wiederholt werden.

D. Einstellungen

  1. Zahnrad öffnen.
  2. Zuggeschwindigkeit und Sound-/Blindmode-Schalter setzen.
  3. Speichern aktualisiert globalen Benutzerzustand.
  4. Registrierte Benutzer werden zusätzlich über /api/users/update persistiert.

6. Partie, Regeln und KI

Regelkern

Chessground stellt das Brett dar; chess.js liefert die gültigen Züge. toDests() bildet daraus die erlaubten Ziel-Felder für die Oberfläche.

KI

Die KI arbeitet lokal mit Minimax und Alpha-Beta-Pruning. Materialwerte und Piece-Square-Tabellen fließen in die Bewertung ein. Die Zugliste wird vor der Suche zufällig gemischt, sodass bei gleichwertigen Bewertungen unterschiedliche Antworten möglich sind.

2026 behobener Fehler: Ältere Annahmen über Zugobjekte führten bei bestimmten Schlagzügen zum Absturz. squareToIndex(), tableValue() und pieceWeight() prüfen Werte jetzt defensiv.

Partiezustand

Der aktuelle Stand wird als FEN in currentGame geführt. Registrierte Benutzer werden über die API in users.json gespeichert; Gäste bleiben nur im laufenden Zustand.

Noch gezielt zu testen

Patt, sonstige Remisfälle, Matt an beiden Seiten, Umwandlung beider Farben und der Fall aiGetBestMove() === null.

7. Trainingssystem

Die Trainingsdaten liegen in app/src/data/training.json. Das Repository enthält außerdem PGN-/Text-/INI-Quellmaterial und einen Parser unter scripts/. Jede Aufgabe besitzt eine Startstellung und eine oder mehrere gültige Zugfolgen.

TrainPlay wählt beim ersten Benutzerzug eine passende Variante und prüft anschließend Zug für Zug gegen diese Variante. Der Gegenzug wird automatisch abgespielt. chapterProgression speichert coursesFinished und completed; zusätzlich existiert coursesFinishedTotal.

Bekannte Starrheit: Das Hauptmenü zeigt derzeit „Kapitel abgeschlossen: x/15“. Die Zahl 15 ist hart codiert.

9. Barrierefreiheit und Audio

Für blinde Nutzer:innen existiert eine eigene Interaktionsschicht: Figurtypen können abgespielt werden; Zug, Schlagzug, Rochade, Schach, Umwandlung, Sieg und Niederlage werden als verständliche Texte in ein verborgenes Informationsfeld geschrieben; der Fokus wird gezielt geführt.

Brettsounds

Normalzug, Schlagzug, Schach, Rochade, Umwandlung, Sieg, Niederlage, Rücknahme und Signalzustände.

Figurensounds

Bauer, Springer, Läufer, Turm, Dame und König besitzen eigene Audio-Dateien.

callHiddenWindow() erzeugt deutsche Ereignistexte wie „weiß beginnt“, „schwarz ist am zug“ oder „Du hast leider verloren.“

Status: implementiert, aber noch nicht systematisch mit Screenreader, Tastatur und allen Soundkombinationen regressionsgetestet.

10. Datenhaltung und Datenflüsse

src/data/users.json ist absichtlich nicht versioniert und wird zur Laufzeit beschrieben. Für einen frischen Checkout existiert users.example.json mit einem leeren Array.

Die Datenbank-Hilfsschicht bietet Lesen, Erstellen, Aktualisieren, Partie-Update und Löschen. Die 2026 ergänzten Schutzprüfungen verhindern, dass update() oder updateGame() bei einer unbekannten ID auf undefined zugreifen.

14. Bekannte Altlasten und Risiken

  1. Framework-Alter: Next.js 12 / React 17; Modernisierung erst nach Regression.
  2. MUI-Mischbetrieb: MUI 4 und MUI 5 gemeinsam.
  3. Weitere latest-Dependencies: insbesondere MediaPipe nicht vollständig eingefroren.
  4. Lokale JSON-Datenbank: geeignet für lokal/demoartig, nicht für Mehrbenutzer-Produktion.
  5. Direkte DOM-Zugriffe: vor allem in FreePlay.tsx und move_displayer.ts.
  6. KI-Endzustände: Patt, Remis und „kein bester Zug“ explizit absichern.
  7. Gast-Defaults: Gastobjekt, Default-Schema und Store-Initialwerte vereinheitlichen.
  8. Hart codierte Kapitelzahl: x/15.
  9. Historisches wantsToClick: Feld existiert, sichtbarer Schalter fehlt; Fix verhindert unbeabsichtigtes Überschreiben.
  10. Debug / ungenutzte Imports: alte console.log-Ausgaben und Imports bereinigen.
  11. Face-Dienst: optional und technisch alt; getrennt prüfen.
  12. Face-Dokumentation: App und Flask verwenden Port 5000; README-Beispiel 5000:3000 sollte korrigiert werden.
  13. PWA: next-pwa installiert, Konfiguration auskommentiert.

15. Betrieb, Installation und Build

Frischer Linux-Start

git clone https://github.com/CopySpotter/Einfach-Schach.git
cd Einfach-Schach/app
cp src/data/users.example.json src/data/users.json
npm install --legacy-peer-deps
npm run dev

Danach: http://localhost:3000.

Prüfung

npm run type-check
npm run build

Beides ist auf dem aktuellen develop-Stand in GitHub Actions erfolgreich gelaufen.

Produktion

npm run build
npm run start

Warum --legacy-peer-deps?

Das Projekt kombiniert ältere Frameworkstände und Bibliotheken. Der Parameter verhindert, dass moderne npm-Peer-Dependency-Regeln die historisch funktionierende Kombination unnötig blockieren.
